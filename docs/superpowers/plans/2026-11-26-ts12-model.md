# TS-12 Model Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Model setting (TS-10 / TS-12) that runs the TS-12's own OS v3.10 with its 76-key keyboard and analog channel pressure, in the machine, the engine, `tsemu` and the app.

**Architecture:** The machine takes `ts::Model` the way it takes its other options; the keyboard model (`Panel`) and the analog mux follow it. The engine passes it through. The app keeps the model last chosen in `settings.xml`, one memory file per model in the Standalone, and one RAM per model in a project state; changing the model restarts the machine on the other OS.

**Tech Stack:** C++17 (cores, machine, engine; MinGW i686, MSVC x64, Linux GCC), JUCE 8 (app), the repo's `tests/check.h` registry and `app/tests/app_tests.cpp`.

**Spec:** `docs/design/2026-11-26-ts12-design.md` (approved 2026-11-26). Read it first: its "What is known" section holds the probe results the tests pin.

## Global Constraints

- The firmware runs unmodified. No JUCE, OS calls or file I/O under `src/`. Nothing in `Machine::runFrame` or `Engine::render` allocates after the boot.
- TS-10 output unchanged: boot trace `ba7e34a4cf23d1e0`; renders `23b6485893beb761` (player_smoke), `0aa23b0ebbdeeec6` (full_chord), `e9d27e034e29b527` (filtered_patch), identical on MinGW i686, MSVC x64 and Linux GCC.
- TS-12 keys: notes 28-103 (E1-G7), key code `k = note - 28`, down `0x80 | k` + strike, up `k` + release byte. No Poly-Key pressure code on the TS-12.
- TS-12 pressure: mux select 1 (U69 Y1), `Analog::Pressure`, rest 0x000; raw 0x100 starts `D0`, 0x280 gives 127.
- TS-12 OS files: `os/ts12_310h.bin` 262 144 bytes, `os/ts12_310l.bin` 524 288 bytes (CRC32 99823433 / 7e64a659).
- Memory files: `ts-memory.bin` (TS-10, unchanged), `ts12-memory.bin` (TS-12). State: `<TSState version="1" ... model="ts12">`, `<RAM model="ts10|ts12">`; no attribute = TS-10.
- Tests never touch the user's settings or memory (`TSR_SETTINGS_DIR`). Firmware tests skip without ROMs.
- Every behaviour choice gets a `docs/decisions.md` entry and `// DECISION <id>` at the point of use. New ids: T31 (model and TS-12 keyboard), A137 (model in the app). Update T17, T8, A115, A116, A117, A125, A126.
- Commits on `plan12-ts12`, `feat(ts): ...` style, scoped by folder.

## Review Focus

1. **A model switch during the boot** (no booted RAM yet): the leaving model keeps its start image, not an empty RAM, so switching back mid-boot loses nothing. Test in Task 6 (`model_switch_during_boot_keeps_start_image`).
2. **A disk in the drive across a switch**: it goes into the new machine, as every other restart does (A119). Test in Task 6 (`model_switch_keeps_disk`).
3. **A TS-12 project opened where the TS-12 ROMs are missing**: the instance becomes TS-12, shows the two missing files, and its RAM waits as the start image; a good ROM folder later boots it with that RAM. Test in Task 6 (`model_state_waits_for_roms`).
4. **The Standalone's memory-file chooser in TS-12 mode** changes the TS-12 file, never the TS-10 one. Test in Task 5 (`settings_memory_file_per_model`).
5. **A host saving right after a switch, before the new boot ends**: the state holds both models' RAM (the left one's as it was, the new one's start image). Test in Task 6 (`model_state_saved_mid_boot_has_both`).

### Task 6: The processor runs a model

**Files:**
- Modify: `app/source/Processor.h`, `app/source/Processor.cpp`, `app/tests/app_tests.cpp`, `docs/decisions.md` (A117, A137)

**Interfaces:**
- Consumes: Tasks 3 and 5.
- Produces: `ens::ts::Model TsProcessor::model() const`; `void TsProcessor::setModel(ens::ts::Model m)`: the settings page's switch, stores `settings_.setModel(m)`; the state load switches with the same private path without storing.
- Members: `ens::ts::Model model_` (constructor: `settings_.model()`); per-model saved memory for Project mode `std::array<std::vector<uint8_t>, 2> modelRam_` and `std::array<std::vector<uint8_t>, 2> modelSelect_` (index `static_cast<int>(Model)`).
- Switch (under `stateMu_`), in order:
  1. Leaving model: File mode, booted → save to `settings_.memoryFile(old)` (A116); Project mode → `modelRam_[old] = ram()` (running RAM if booted, else the start image, Review Focus 1), `modelSelect_[old] = select(snapshot)`.
  2. `model_ = m`; ROMs from `romFolder_` via `checkRomFolder(romFolder_, m, &roms)`. A problem: the engine is released (`suspendProcessing`, `engine_.reset()`, `cd_.setEngine(nullptr)`), `romError_` names the missing files, and the next start image is set as in step 3 (it waits, Review Focus 3); return.
  3. Start image: Project mode → `modelRam_[m]` if not empty, else `loadMemoryFile(settings_.memoryFile(m), ...)`; File mode → the model's memory file. `startSelect_ = modelSelect_[m]` (empty when none). `restored_` cleared and `restoreWanted_ = false` (media are not kept across a switch: a ponytail limit, the user loads the sampled sounds again; note it in A137).
  4. `restart(Ram::Start)`; `Engine::create(roms_, e, true, true, model_)` there.
- Every `settings_.memoryFile()` becomes `settings_.memoryFile(model_)`; `findRomFolder(..., model_)` and `checkRomFolder(..., model_, ...)` in the constructor and `setRomFolder`.
- State: `getStateInformation` writes `model="ts10|ts12"` on `<TSState>`, `<RAM model="...">` for the running model (as now, A117) and, when `modelRam_[other]` is not empty, a second `<RAM model="other">`. `setStateInformation`: `model` attribute (absent = ts10); each `<RAM>` by its `model` (absent = ts10) into `modelRam_`; when the state's model differs from `model_`, switch (not stored), then restore the running model's RAM as A117/A129 do now.
