# TS-12 model: design

2026-11-26. Builds on the TS-10 emulator (`docs/design/2026-11-13-ts-emulator-design.md`, section 2: the TS-12 is
in scope again since 2026-11-26, the user's decision).

## Intent

The user's to-do: "check TS-12 vs TS-10 differences and add features". The TS-12's features (14 Touch curves,
PRESS-MODE, release velocity, 76 keys) live in its own OS, and the firmware runs unmodified (AGENTS.md), so they
cannot be added to the TS-10 OS. The way to have them is to run the TS-12 OS v3.10 as a second model of the same
instrument. A TS-12 user gets their instrument; a TS-10 user loses nothing.

## What is known (research, 2026-11-26)

Throwaway probes on the current machine, the user's `roms/os/ts12_310h.bin` and `ts12_310l.bin` in place of the
TS-10 pair, the six other files unchanged:

- **It boots as it is.** The OS shows `ENSONIQ TS-12`, calibrates the keyboard and reaches the play screen
  (U0-0 BABY-GRAND ...) on the same machine. Service manual p5: same boards, different OS EPROMs, a 76-key
  weighted keyboard with mono pressure. T2's interleave holds (the upper half of the l file is identical).
- **Keys** (the T17 sweep repeated): key down is `0x80 | k`, then the strike value; key up is `k`, then a byte.
  Note = k + 28: codes 0x80-0xD0 gave notes 28-108, so the 76 keys E1-G7 (MIDI 28-103) are k = 0-75. Codes
  0x00-0x7F alone (no key down) and 0xD1-0xFF with or without a key held gave nothing on MIDI out: there is no
  Poly-Key pressure code.
- **Velocity.** With the default Touch, strike to MIDI velocity (k = 24, note 52, a white key): 1→1, 22→3, 43→7, 64→20,
  85→39, 92→52, 99→63, 106→74, 113→95, 120→127. The TS-10 table (T17) gives 92 at 64. So the same strike byte
  means something else; what it is physically is not known (as on the TS-10).
- **Release velocity.** The key-up byte is used: note-off velocity follows it on the same curve (64→20,
  99→68, 113→110), where the TS-10 always sends 64.
- **Pressure is analog.** The TS-12 OS adds mux select 1 (U69 Y1, not connected on the TS-10) to its cycle:
  `0 2 5 3 4 1` against the TS-10's `0 2 5 3 4`. Raw Y1 0x000-0x080 sends nothing, 0x100 starts channel
  pressure (`D0 nn`), 0x280 and above gives 127; the OS filters it (several steps per change). It is sent with or
  without a key down. Raw 0 is "no pressure".
- **Manual** (`datasheets/TS-12 Musician's Manual.pdf`): 76-note weighted action; Channel Pressure from the
  keyboard, Poly-Key pressure received over MIDI; 14 Touch settings (PNO-VEL1-6, SYN-VEL1-6, FIXED-64,
  FIXED127); System page PRESS-MODE (CHAN or PSET). The same 300 sounds, panel, jacks and options (SW-10,
  SQX-70, SP-4, sample RAM).

## Goals

- A **Model** setting, TS-10 or TS-12, in the Standalone and in each plugin instance. TS-10 is the default until a TS-12 is chosen; after that the last choice is (see "Which model starts").
- The TS-12 runs its own OS v3.10 with its keyboard: 76 keys, its key codes, a meaningful key-up byte, and
  pressure on mux Y1.
- The two TS-12 OS files ship in git and in the release folder beside the TS-10's six (the user's decision,
  2026-11-26).
- `tsemu --ts12` and firmware tests for the TS-12, skipping without its ROMs as the TS-10 tests do.

## Non-goals

- Grafting TS-12 features onto the TS-10 OS (the firmware runs unmodified).
- An on-screen pressure control. MIDI keyboards' pressure already reaches the OS through MIDI IN, which it reads
  itself (channel and Poly-Key). The on-screen keyboard gets pressure, if at all, with the dockable-keyboard work.
- The panel logo. The panel keeps its current art; the logo item on the to-do list (TS-RB logo, TS-10 logo) decides
  what a TS-12 shows.
- Other TS-12 OS versions (3.05 stays ignored, as the TS-10's older versions are).

## Anti-goals

- Any change to the TS-10's output: the boot trace and the three render hashes stay as they are.
- A TS-10 battery memory or project state silently loaded into a TS-12, or the other way round.

## Constraints

- AGENTS.md: no JUCE or file I/O under `src/`; the render path stays real-time safe; tests never touch the user's
  settings or memory; the firmware runs unmodified; MAME is not a reference.
- The ROM rule in AGENTS.md, README, `roms/README.txt`, `.gitignore`, `tools/dist.ps1` and `tools/dist.sh` changes
  from six files to eight. A126/A125: the release copies all eight, beside the program and inside the VST3; "holds
  the ROMs" (A125) means the files the chosen model needs.
- A user's ROM folder from before has six files: the TS-10 must keep working from it; the TS-12 reports its two
  missing files as today's ROM errors do.

## Approaches

- **A. One app, a Model setting (chosen by the user, 2026-11-26).** The machine takes the model like its other
  options (SQX-70, SCSI, 8 MB); the app offers TS-10 / TS-12 on the settings page, kept per instance. Fits the naming
  decision (design section "Names": the plugin is not called TS-10 so a TS-12 can join it).
- B. Two plugins, "TS Reborn 10" and "TS Reborn 12": clear per instance, but twice the builds, IDs and release
  contents, against the naming decision.
- C. No setting, the app runs whichever OS is in the ROM folder: nothing to choose, but the release ships both, so
  it needs a rule anyway, and switching means moving files.

## The design (A)

**Machine.** `Machine::create` takes the model (as it takes `sqx70`, `scsi`, `simm8`). `RomSet` keeps the OS pair
it is given; the caller chooses which files to read. With the TS-12:

- The keyboard model (`Panel`) encodes keys as `0x80 | (note - 28)` for notes 28-103, and sends the key-up byte the
  caller gives instead of a fixed one.
- Mux Y1 is a real input, `Analog::Pressure`, resting at 0. On the TS-10 it stays unconnected as now.
- `Machine::pressure(note, amount)` has no Poly-Key form on a TS-12. The builder decides whether it maps to Y1
  (channel pressure) or is ignored there; the app does not call it today.
- New decision entries: the model (machine), the key codes and the pressure input (in `docs/decisions.md` and
  `docs/ts-hardware-interface.md` "Keys and pressure", "Analog inputs"), with the probe results above as evidence,
  each re-checked by a committed firmware test.

**Engine.** `Engine::create` passes the model through. Key events carry the key-up byte. Nothing else in the render
path changes.

**App.**
- **Model** on the settings page (TS-10 / TS-12). Changing it restarts the machine on the other OS, after the
  current memory is saved, as the other restart paths do.
- **Which model starts.** `settings.xml` (shared by the Standalone and the plugins) keeps the model last chosen on
  any settings page. The Standalone and every new plugin instance start as that model (the user's decision,
  2026-11-26), so the constructor knows the model, picks the ROM folder for it (A125) and boots it before any
  state arrives. A loaded project state's model wins for that instance only and does not change the setting.
- Standalone: each model has its own memory file: `ts-memory.bin` for the TS-10 (unchanged, so existing memories
  stay), `ts12-memory.bin` for the TS-12, each changeable as now (per model).
- Plugin: the project state keeps **one memory per model** (the user's decision, 2026-11-26): `<TSState ...
  model="ts12">` names the running model, and each `<RAM>` names its model (`<RAM model="ts10">`, `<RAM
  model="ts12">`). Switching an instance's model keeps the memory it leaves in the state; switching back restores
  it exactly. A model the instance has not run yet starts from that model's shared memory file, as a new instance
  does. An older state (no `model` attributes) is a TS-10 state with one TS-10 RAM. A state's RAM is never restored
  into the other model. `select` and `<Media>` belong to the running model; the builder decides whether the left
  model's are kept too (keeping them is the closer match to "switching back restores it").
- **Memory images are not identified** (the builder's call, settled in review): a 512 KB image says nothing about
  the OS that wrote it, so the chooser, "Copy to shared memory" and `tsemu --ram` trust the user; the default file
  names and the state's `model` attributes are the guard. The builder checks and records what each OS does when it
  boots on the other's image.
- **A model whose ROMs are missing** (the builder's call, settled in review): the switch takes effect; the machine
  stops and the display and settings page name the missing files, as a start with a bad ROM folder does. A loaded
  TS-12 state must behave this way anyway; its memory waits as the start image until the ROMs are there.
- On-screen keyboard: the TS-12 draws 76 keys, E1-G7, in the keyboard's current width (narrower keys); the TS-10
  keeps its 61. The strike still comes from where the key is clicked (A115); the builder sets the TS-12's strike
  range so that the click range covers soft to loud on its curve (strike about 1-120 per the table above) and
  sends the strike as the release byte (A115 already carries it).
- ROM folder checks name the files of the selected model; the settings page shows which model's files are missing.

**Release.** Eight ROMs, beside the program and inside the VST3 package. `roms/README.txt` lists the TS-12 pair.

**tsemu.** `--ts12` reads `os/ts12_310h.bin` and `os/ts12_310l.bin` instead of the TS-10 pair (for `boot`,
`render` and `bench`).

**Tests.** With the TS-12 ROMs: it boots to the play screen and shows `TS-12`; a key at note 28 and at 103 sounds
and goes out as `90 1C`/`90 67`; the key-up byte changes the note-off velocity; Y1 raised gives `D0` on MIDI out.
App checks: the model setting (a new instance follows the last choice; a loaded state does not change it),
per-model memory files, a TS-12 state round trip, a TS-10 state into a TS-12 instance switching it, a switch and
switch back restoring the first model's RAM byte for byte, an old state without `model` loading as TS-10, a ROM
folder with six files (TS-10 fine, TS-12 reporting two missing). Real-time suite: a TS-12 boot
allocates nothing in `runFrame`/`render`. The TS-10 hashes unchanged on all three toolchains.

## Left to the builder

- Names (`Model` enum, its spelling in settings and state), how `Panel` holds the model, test names.
- Whether `Machine::pressure` drives Y1 on a TS-12.
- The exact TS-12 strike range and how many probe points the tests pin.
- Where the Model control sits on the settings page, and its wording.

## User to run

- Play the TS-12 from a MIDI keyboard: Touch curves, pressure (channel), release velocity on a sound that uses it.
- Switch models in the Standalone and in a DAW; reopen a project of each model.
